# CoffeeGo — Мобільний додаток та веб-кабінет кав'ярень

## Опис проєкту
Проєкт призначений для швидкого попереднього замовлення кави без черг, використання накопичувальної системи бонусів та автоматизації роботи баристи і менеджера мережі[cite: 15, 22].

Тип системи: Cross-platform Mobile App (iOS/Android) + Web SPA (Панель баристи/менеджера) + REST API Backend.

---

## Стек технологій (Tech Stack)

### Client Side (Мобільний додаток & Web)
Mobile App: Flutter (Dart) — кросплатформова розробка під iOS (v14.0+) та Android (v9.0+).
Web UI (Кабінет баристи та менеджера): React.js / Vue.js — Single Page Application (SPA) для планшетів кав'ярні[cite: 18].
State Management: Provider / Bloc.

### Backend & Database
API Framework: Node.js (NestJS) / Python (FastAPI) — REST API сервіс[cite: 18].
Database: PostgreSQL — основна реляційна база даних для користувачів, замовлень та меню[cite: 18].
Authentication: JWT (JSON Web Tokens) + HTTPS (TLS 1.3)[cite: 18].

### Інтеграції та сервіси
POS-система: Двостороння інтеграція через REST API з POS-системою кав'ярні (Poster/iiko)[cite: 18].
Платіжний шлюз:

 Apple Pay, Google Pay SDK, LiqPay / MonoPay[cite: 18].
Push-сповіщення: Firebase Cloud Messaging (FCM) / Pusher для сповіщень про стан замовлення[cite: 18].

## Використовувані технології
- **Backend:** C# / ASP.NET Core
- **Database:** PostgreSQL
- **Frontend:** React / TypeScript

2. **За яким критерієм визначають, що лишити в README репозиторію, а що винести у вікі проєкту?**
   У README залишають лише технічні деталі, тісно пов'язані з кодом (команди запуску, конфігурацію, приклади API), які потрібні розробнику для швидкого ознайомлення за «правилом 30 секунд»[cite: 4, 6]. У вікі (Notion) виносять довгоживучу документацію, ТЗ, деталізовані вимоги та описи бізнес-процесів для всієї команди й замовника[cite: 4, 6].

3. **З яких трьох частин складається класичний ADR і що фіксує кожна з них?**
   * **Контекст:** Фіксує вихідну проблему, обмеження та умови прийняття рішення[cite: 5, 6].
   * **Рішення:** Фіксує обрану технологію або архітектурний підхід[cite: 5, 6].
   * **Наслідки:** Фіксує результати вибору — як переваги, так і компроміси й обмеження[cite: 5, 6].

4. **Чому ADR не редагують заднім числом, коли рішення змінюється?**
   ADR фіксує точний історичний контекст прийняття рішення на конкретний момент[cite: 4, 5, 6]. При зміні підходу старий ADR переводять у статус `superseded` або `deprecated`, а для нового рішення створюють наступний файл ADR[cite: 6].

5. **Що означає статус ADR «proposed» на відміну від «accepted»?**
   Статус `proposed` означає, що рішення запропоноване й перебуває на обговоренні, а `accepted` — що воно затверджене командою як обов'язковий стандарт[cite: 5, 6].

6. **Чому документація, яка розходиться з реальним станом проєкту, часто шкідливіша за її відсутність?**
   Застаріла документація дезінформує розробників, змушує марнувати час на відлагодження непрацюючих інструкцій і повністю руйнує довіру до документаційної бази проєкту[cite: 6].
